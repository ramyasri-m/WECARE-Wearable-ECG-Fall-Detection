# Mobile App — What Went Wrong and How to Fix It

Honest post-mortem of the `mobile/` directory on this branch, and a
concrete path to a working build.

## What's actually broken

The directory looks like a React Native project but **cannot be built**
as-is. The commit contains **17 files** when a real React Native 0.76
scaffold has ~60+ files. The missing pieces:

| Missing | Why it matters |
|---------|----------------|
| `package.json` | Without it `npm install` has nothing to read — the project has zero dependencies installed |
| `android/gradlew`, `gradlew.bat` | Shell scripts that drive the Android build. Without them `./gradlew assembleDebug` fails |
| `android/gradle/wrapper/gradle-wrapper.jar` | Binary file — Gradle refuses to start without it |
| `android/app/debug.keystore` | Binary file — `signingConfigs.debug` references it; build fails on sign step |
| `android/app/src/main/res/mipmap-*/ic_launcher*.png` | Launcher icons the AndroidManifest references via `@mipmap/ic_launcher` |
| `android/app/src/main/res/values/styles.xml` | Theme `@style/AppTheme` referenced in the manifest |
| `metro.config.js` | Metro bundler config — RN won't start without it |
| iOS project (`ios/` folder, `Podfile`, Xcode project) | Entire iOS build target absent |
| `.gitignore` for `node_modules` | If you ran `npm install` the repo would blow up with 300MB of deps |

## Root cause

I wrote the source files assuming `npx react-native init` had already
run. I did not run it, so none of the generated boilerplate exists.
Several of the required files are **binaries** (`.jar`, `.keystore`,
`.png`) that cannot be committed via text-based tool calls — they must
be generated locally.

## The scanner also wasn't the right first thing to build

The React Native app on this branch scans for *any* BLE device nearby
and labels them by RSSI. That demonstrates that BLE scanning works on a
phone — but it is not what the WECARE paper actually needs. What WECARE
needs on the mobile side is:

- **Receive** emergency alerts (push notification + instructions screen)
- **Display** the LLM-generated bystander instructions clearly
- **Report back** `bystander_acknowledged` to the orchestration engine

The scanner was built because the professor said "detect bluetooth
devices nearby," but the orchestration layer already simulates that
part. The mobile-side gap is **the bystander receiving the alert**, not
scanning.

## The fix — one of two paths

### Path A — If a native React Native app is required

```bash
# From a working dev machine with Android Studio installed:
npx @react-native-community/cli@latest init WECAREMobile --version 0.76.5
cd WECAREMobile

# Install BLE and permissions
npm install react-native-ble-plx@^3.2.0 react-native-permissions@^4.1.5

# Copy the custom source files from this repo
cp -r ../WECARE/mobile/src ./src
cp ../WECARE/mobile/App.tsx ./App.tsx

# Add BLE permissions to android/app/src/main/AndroidManifest.xml
# (see mobile/android/app/src/main/AndroidManifest.xml in this repo)

# Build and run on a connected phone
npx react-native run-android
```

The source files already on this branch (`BLEScannerScreen.tsx`,
`DeviceCard.tsx`, `ntfyService.ts`, `bleUtils.ts`) are the custom logic
and are correct. They just need to drop into a real scaffold.

### Path B — Skip native, use a PWA (recommended for demo)

The existing `index.html` is already the full dashboard. Make it
installable with ~20 lines:

1. Add a `manifest.json` pointing at the existing site
2. Add a service worker that caches the page shell
3. Visit the site on Android Chrome → "Add to Home Screen"
4. The site now opens full-screen like an app, receives ntfy push
   notifications, and runs the same dashboard

Zero native code, no gradle, no Android Studio, works today on an
already-deployed GitHub Pages URL. This is probably what the professor
actually wants to see at the demo.

## What this branch should ship instead

Rather than trying to patch the broken scaffold, this branch now adds
the thing that is **genuinely new and useful**: a multi-agent
orchestration layer (`wecare_agents.py` and `docs/MULTI_AGENT_ARCHITECTURE.md`).

The multi-agent system replaces the single monolithic LLM call with
specialized agents (Triage, Bystander Instructor, Paramedic, Patient
Reassurance, Coordinator) that run in parallel and talk to each other.
That is a real architectural improvement to the paper's "multi-actor
coordination" claim — not a surface-level feature.

The mobile code is left in place for reference but should not be
treated as runnable until Path A or Path B is executed.
